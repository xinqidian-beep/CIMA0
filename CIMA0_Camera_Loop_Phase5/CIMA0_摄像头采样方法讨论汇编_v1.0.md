# CIMA0 摄像头采样方法讨论汇编 v1.0

> 本文档梳理围绕"摄像头采样"这一层，从最早发现的问题到最终收敛设计，
> 讨论过的**全部**方法、每种方法被采纳/否决的理由、以及仍然悬而未决的部分。
> 按讨论的逻辑演进顺序排列，不是按重要性排列——后面的方法往往是对前面方法的修正或叠加，
> 建议按顺序读，能看出这条思路是怎么一步步收窄到最终版本的。

---

## 0. 起点：最早发现的问题

最初代码里的采样是 `bytes_to_blocks` 只取**前 128 字节**（画面顶部 4 行），这是问题的起点——不是"降采样"本身有问题，而是**截断丢弃**：96% 的画面信息从未参与任何计算。这直接催生了后续所有讨论共同遵守的第一条底线：

> **摄像头输入不能被截断/降采样丢弃——要么全采，要么均匀覆盖。**

后续所有方法都在满足这条底线的前提下展开。

---

## 1. 被否决 / 已弃用的方法

### 1.1 顶部字节截断（`bytes_to_blocks` 原始版本）
- **做法**：只取画面数据流的前 128 字节。
- **否决理由**：直接违反"不截断"原则，96% 画面信息被丢弃，且丢弃的是固定位置（顶部），带有隐含的空间偏见。

### 1.2 `cv2.resize` 到写死常量尺寸
- **做法**：`cv2.resize(frame, (64, 64))` 或类似，目标尺寸是代码里的固定数字。
- **否决理由**：
  - 表面上不再"截断"，但插值本身是不透明的加权近似，不是每个原始像素被公平计入某个输出格子（不满足"均匀覆盖"的字面要求）；
  - 更关键的问题是目标尺寸（64、16×10 等）是**外部一次性写死的常量**，不随摄像头原生分辨率变化，违反"Cell 拓扑不该是外部写死"这条原则；
  - 这个问题不是某一版代码独有的——从早期的 v9.0.2 到后来的 v7.2-color（`DOWN_W, DOWN_H = 16, 10`），这个写死常量的模式反复出现，说明"拓扑该怎么从输入结构派生"这件事从未被真正解决过，只是数字不停变。

### 1.3 `open_clip` 自带预处理管线（`preprocess`：Resize + CenterCrop 224×224）
- **做法**：GitHub 实际代码里 `ClipRegion.encode()` 直接调用第三方库自带的标准图像预处理，把它当成系统的采样层。
- **否决理由（三重违反）**：
  - `CenterCrop` 直接裁掉画面四周，等于又一次"取一部分、丢弃其余"，是 1.1 那个问题换了个方式复现；
  - `224` 这个目标尺寸来自库内部（模型架构决定），比自己写死常量更进一步——连"写死"这个决定本身都不是自己做的；
  - 把第三方库的预处理假设直接当成系统架构的一部分，等于让 `open_clip` 拥有了"特权采样通道"，违反"open_clip 不是外挂翻译器"这条原则。
- 这一处被认定为**当前代码里最严重的一处偏离**，且尚未确认是有意的架构转向还是遗漏。

### 1.4 基于运动强度的 Top-K 选择性采样（早期 `DummyCamera`/`RealCameraPeripheral` 阶段）
- **做法**：`flat_indices = np.argsort(diff.flatten())[::-1][:15]`，只对运动最强的前 K 个格子发射刺激，其余格子完全不参与。
- **否决理由**：这是一种选择性丢弃——虽然理由（"运动才重要"）在后期被部分保留（见 §2.6 运动优先原则），但**完全跳过**未入选格子、不给它们任何输出，和后来收敛的"粗算基线 + 精算补充"模式不同——后者保证所有格子始终有输出，只是精细程度不同。

### 1.5 采样密度随算力离散跳变（`camera_size` 在 16/32/64 之间硬切换）
- **做法**：`CameraObserver.update_resource()` 根据 `compute_state["available"]` 的阈值（0.7、0.3）在三档密度间切换。
- **否决理由**：
  - 密度一变，`grid_h × grid_w` 瞬间跳变，整个网格拓扑不连续，下游如果基于网格尺寸构建了 Cell 网络（邻接关系、历史状态），每次跳变都要推倒重建；
  - 如果 `available` 数值在阈值附近抖动，会导致网格反复重建，是先前讨论过的"抖动/迟滞"问题的又一次重现；
  - 这个方案后来被 §3 的"固定拓扑 + 预算内精算"整体取代——用"格子数量恒定、精算格子数量随算力变化"替代"格子本身的数量随算力变化"，从根源上消除了拓扑跳变问题。

## 2. 被采纳并保留下来的方法（按讨论顺序）

### 2.1 空间保结构的确定性块遍历（`bgr_to_spatial_blocks`）
- **做法**：按固定 `block` 尺寸逐块扫描全画面，位置由二重 `for` 循环确定性给出，不使用任何随机采样。
- **状态**：✅ 采纳。满足"不截断/均匀覆盖"，也满足"避免随机取块"这一后来单独提出的要求——这版代码本身在被检查时就已经符合，不需要额外修改。

### 2.2 块平均（reshape + mean）替代插值
- **做法**：
  ```python
  trimmed = frame[:H*cell_px, :W*cell_px]
  patches = trimmed.reshape(H, cell_px, W, cell_px, 3)
  grid = patches.mean(axis=(1, 3))
  ```
- **状态**：✅ 采纳，作为 §1.2 的替代方案。每个原始像素恰好、只属于一个 cell，贡献权重完全相等，不像插值那样用不透明权重"猜"。

### 2.3 拓扑由分辨率派生（`N = DOWN_W * DOWN_H`）
- **做法**：格子数量和网格连接关系（`build_grid_neighbors`）由 `DOWN_W, DOWN_H` 直接计算得出，而 `DOWN_W, DOWN_H` 本身建议从摄像头原生分辨率 ÷ 一个"密度旋钮"参数（如 `cell_px`）算出，而不是直接写一个常量。
- **状态**：✅ 原则已确认，但**实现层面从 v7.2 到最新 Phase3 代码都未曾真正做到**——密度旋钮本身还是常量，只是从"格子数"这个常量换成了"每格像素数"这个常量，本质上仍是外部一次性给定。这是一个**尚未真正解决、只是反复搬家的问题**，需要在下一次实现里明确用摄像头运行时读到的实际分辨率去做除法，而不是继续写死任何一边。

### 2.4 竞争认领（`claim_score`）
- **做法**：每个输入块由邻近若干 Cell 竞争认领，评分 = 结构相似度权重 × 相似度 + 可用性权重 × 可用性 + 新鲜度权重 × 新鲜度，胜者获得这次输入，权重本身可作为 Cell 内生慢变量随经验漂移（需满足慢更新 + 有界的两个限制）。
- **状态**：✅ 采纳，是"注入不能是外部指定谁对应谁"这条原则的直接实现。在 v9.0.2 审计中发现这个机制一度被替换成固定权重线性叠加（倒退），v7.2-color 版本保留了完整实现，可作为参照。

### 2.5 BGR 全程不转换
- **做法**：采集、分块、Cell 内部状态、显示输出，全程使用 BGR 数值，不做 `cvtColor` 转 RGB；若显示后端默认按 RGB 解释导致偏色，选择接受偏色或换用原生支持 BGR 的后端，而不是加一道"纠正性"转换。
- **状态**：✅ 采纳，是目前所有讨论过的方法里少数被确认"完整且正确"、未出现反复的一条。

### 2.6 运动优先、色阶为副信号
- **依据**：现实中物体自发变色的情况远少于运动，所以运动该是主信号，色阶该是附加/门控信号，不是并列独立通道。
- **做法**：
  ```python
  motion = np.abs(gray - previous_gray)
  color_delta = np.abs(color - previous_color).mean(axis=2)
  color_delta *= (motion > threshold)     # 门控：静止区域色阶差清零
  score = motion + weight * color_delta
  ```
- **状态**：✅ 采纳。`weight` 系数（讨论中用了 `0.3`）目前没有推导依据，是待校准参数（见操作手册 §5）。

### 2.7 自比较原则（δ = 当前状态 − 自身历史状态）
- **依据**：运动信号和色阶信号要能在同一把尺子上比较，必须都取"自己和自己比"的差值，而不是比较两个异质的量（比如"运动的变化量"vs"色阶的绝对值"）。这个原则让两个信号在结构上天然同构，竞争才公平。
- **状态**：✅ 采纳，是 §2.6、§2.8 里所有"竞争评分"机制的共同数学基础。

### 2.8 人眼式聚焦（中央凹）——两种实现路径的取舍

**路径 A（已否决）：真正的非均匀密度网格**
- 中心区域格子密、边缘稀疏，格子本身的空间分布不均匀。
- **否决理由**：与"输出形状恒定/同构"这条后期确立的约束冲突——注视点移动或密度变化会导致输出结构本身发生变化，且 `build_grid_neighbors` 的规整矩形邻接假设不再成立，需要重新设计非规整拓扑下的邻接关系，复杂度陡增。

**路径 B（已采纳）：格子位置不变，只做竞争评分的空间加权**
- **做法**：
  ```python
  fovea_center：运动质心的指数平滑跟随（跟随速度 0.3）+ 无运动时向中心缓慢回归（衰减 0.95）
  fovea_weight = 1 / (1 + fovea_strength * 距注视点距离²)
  score = (motion + weight * color_delta) * fovea_weight
  ```
- **状态**：✅ 采纳。网格形状、数量完全不变，只是"同样大小的 δ，离注视点越近的格子越容易在竞争里胜出"。`fovea_strength`（用了 `1.6`）、跟随速度、回归速度三个系数均为待校准参数。
- **遗留问题**：算运动质心这一步涉及一次"空间统计计算"，是否算越过了"observer 不理解图像"的边界，讨论中给出的判断是"这是纯空间统计、不涉及语义判断，倾向于认为不越界"，但这个判断本身未被追溯到某条已确立原则的直接推论，标记为一个需要持续关注的灰色地带。

### 2.9 动画式色阶量化（posterize）
- **做法**：
  ```python
  step = 1.0 / (tone_levels - 1)
  posterized = np.round(color / step) * step
  ```
- **状态**：✅ 采纳，作用于色彩通道数值本身，不影响拓扑，与 §2.8 路径 B 正交、可直接叠加。级数（讨论中用了 `5`）是待校准参数。
- **讨论中曾提出的一个未采纳的延伸**：色阶量化是否该只作用于亮度/明度通道（先转 HSV/Lab），保留色相连续，更贴近赛璐璐"分层上色、色相不断层"的实际做法——这一版本更精细，但目前的实现是对 BGR 三通道各自独立量化，尚未按这个方向细化，留作后续可选的精化方向。

### 2.10 固定拓扑 + 算力预算驱动的精算/粗算分层（最终收敛的核心设计）
- **做法**：
  1. 全画面粗算基线（§2.2 块平均）**永远发生**，输出形状 `(grid_h, grid_w)` 恒定；
  2. 竞争评分（§2.6+§2.7+§2.8+§2.9 综合）算出每个格子的举手强度；
  3. `ComputeSystem` 独立算出的算力比例，换算成"这一帧能精算几个格子"（`n_precise = int(n_cells * available)`）；
  4. 评分最高的 `n_precise` 个格子获得"精算"（重新计算，理论上可以比粗算更细致，如保留完整色彩块而非压成标量）；
  5. 落选格子保留粗算结果，**不是空值、不是缺失**，只是精细程度较低。
- **状态**：✅ 目前的最终版本，同时满足：不截断（基线永远覆盖全画面）、拓扑恒定（不随算力/注视点变化）、职责分离（compute 只给预算数字，不理解内容；observer 只用预算数字，不索取更多）。
- **遗留问题（"精算"具体该做什么，尚未定案）**：当前占位实现里，"精算"只是对赢家格子重新算一次均值，数值上和粗算结果完全相同，没有实质内容。需要明确精算该输出什么额外信息（保留完整色彩块？子网格细分？更高阶统计量？），这个决定会影响输出结构是否还能保持单一矩阵形式，还是需要变成"结构恒定的一组矩阵"（如粗算主矩阵 + 稀疏的精算色彩块字典）。

### 2.11 `cv2.INTER_AREA` 作为块平均的高效等价实现
- **做法**：`cv2.resize(frame, (grid_w, grid_h), interpolation=cv2.INTER_AREA)`，缩小场景下等价于像素面积加权平均，数学上和 §2.2 的 reshape+mean 一致（整数缩放比例时严格相等），但是 C++ 实现，调用次数从 O(格子数) 降到 O(1)。
- **状态**：✅ 采纳为效率最优解，且明确澄清它不属于 §1.2 否决的"插值"范畴——`INTER_LINEAR`/`INTER_CUBIC` 是不透明加权插值（该被否决），`INTER_AREA` 在缩小场景下是确定性面积平均（不违反"均匀覆盖"）。这个区分是本轮讨论里唯一一次对"插值"这个词做的精确拆分，值得记住：**否决的是插值的不透明加权本质，不是"用了 resize 这个函数名"本身**。

## 3. "举手"机制与外部接口（贯穿全程的输出规范）

- **原则**：外部（下游/观察者）不读取内部状态细节，只读一个简单信号（"举手"——哪些格子活跃、活跃到什么程度）。
- **在采样层的体现**：`CameraObserver.snapshot()` 只暴露 `camera_size`、`shape`、`mean`、`std` 这类聚合统计量，不暴露完整状态矩阵本身作为主要读取接口。
- **状态**：✅ 原则已确认；在早期版本（v7.2-color 的 `Cell.raised` 布尔标记 + `ObservationSystem.capture` 只返回 `raised=True` 的 Cell）里有完整实现；在最新 GitHub 代码（Phase3）中被审计发现**整体缺失**——`main.py` 实际运行的 `archive/observer.py` 直接返回连续统计量（`local_signal`），没有举手筛选这一步，是已记录的待修复项。

## 4. 当前仍未解决 / 需要下一步明确的问题清单

1. **"精算"具体输出什么**（§2.10 遗留问题）——目前是占位实现，无实质内容。
2. **`DOWN_W, DOWN_H`（或等价的密度参数）如何真正从摄像头运行时分辨率反推**，而不是继续写一个常量（§2.3 状态：原则确认但从未真正落地）。
3. **色阶量化是否该转到 HSV/Lab 只量化明度通道**，保留色相连续性（§2.9 未采纳的延伸）。
4. **一批待校准的数值系数**：色阶权重 `0.3`、聚焦强度 `1.6`、注视点跟随速度 `0.3`、回归速度 `0.95`、色阶级数 `5`——全部没有推导依据，目前允许暂用但需在操作手册的待校准表里持续追踪。
5. **举手机制在最新代码里的缺失**，需要在接入 `CameraObserver`/`CameraComputeSystem` 到实际管线时一并补上，不能只修接线问题、漏掉这一层。
6. **算运动质心是否算越过"不理解图像"边界**（§2.8 遗留问题）——目前倾向于认为不越界，但缺少直接的原则推导支持这个判断，需要持续关注，不作为已定案处理。

## 5. 贯穿全程的主线：模块自治，工程师不介入模块职责内的事

上面 §1、§2 罗列的是"方法对不对"，这一节单独把每个方法背后**"这个决定该谁来做"**这条线摘出来。
这条线才是这整场讨论真正在收敛的东西——采样精度、密度、权重、精算与否，表面上是一堆技术参数，
实质上每一个都在回答同一个问题：**这个数字，是外部一次性规定的，还是模块自己依据事实推出来的？**
按这把尺子重新过一遍前面所有方法：

| 决策点 | 讨论中出现过的"工程师越权"版本 | 最终收敛的"模块自治"版本 | 谁该拥有这个决定 |
|--------|------------------------------|--------------------------|----------------|
| 采样目标尺寸 | `H, W = 64, 64` / `DOWN_W, DOWN_H = 16, 10`：工程师直接写一个数字 | 尺寸由摄像头原生分辨率 ÷ 密度旋钮反推（**注：此项仅原则确认，实现从未真正做到**，见 §4.2） | `CameraPlanet`/采样模块自己，依据它接到的帧的实际形状 |
| 采样密度随算力变化 | `update_resource` 里工程师写死阈值（0.7/0.3）和对应密度（16/32/64），本质是把"该多细"这件事的判断权放在了固定的 if-else 里，而不是模块的连续计算 | 拓扑恒定，只有"精算名额数量"随预算连续变化（`n_precise = int(n_cells * available)`） | `ComputeSystem` 决定预算数字；`CameraObserver` 决定怎么花这笔预算，两者各管一段，工程师只做转发 |
| 谁的信息该被精算 | 早期 Top-K 运动强度硬编码"只留前 15 个"，K 是工程师定的常量 | 举手竞争：格子自己算出 δ，按 δ 排名，名额数量由预算决定，工程师不参与排名过程 | Observer 内部的竞争评分逻辑 |
| 认领谁的输入 | 早期设想"外部指定哪个像素对应哪个 Cell" | `claim_score` 竞争认领，权重本身是 Cell 的内生慢变量，随自己的经验漂移 | 每个 Cell 自己 |
| 注视点在哪 | 曾经讨论过"固定在画面正中央"，本质是工程师替系统决定了"该看哪" | 运动质心的指数平滑跟随，中心位置由观察到的运动数据算出来，不是写死坐标 | Observer 内部的 `_update_fovea` 逻辑 |
| CLIP 的介入方式 | 曾经出现过 `open_clip` 预处理直接当采样层，等于把"该怎么采样"这个决定完全交给了第三方库的默认假设，工程师连自己决定的机会都放弃了，直接借用了外部权威 | CLIP 该被当作"世界里的一个结构"参与局部竞争，而不是获得特权广播通道 | 尚未真正实现，是当前最严重的一处越权（连"谁决定"这个问题都还没被问过，直接被库的默认值替代了） |
| 色阶量化级数、聚焦强度等系数 | 讨论中这些数字（`0.3`、`1.6`、`5`）都是**我拍出来的**，没有经过任何模块内部的计算过程 | 尚未收敛——按判据，这些理想情况下也该是模块能自己校准的量，目前只是老实承认"还没做到"，登记进待校准表，不假装已经解决 | 长期看应属于对应模块自己的内生慢变量；短期允许工程师暂定初值，但必须标注为暂定，不能当作定案 |

### 5.1 这条主线的一个更精确的判断标准（比"看起来像不像"更可操作）

判断一处采样代码有没有违反自治，不要看"这行代码写在哪个模块里"，要看**这个数字的来源能不能追溯到某个模块自己的状态或历史**。同一个动作，两种写法看起来都在"模块内部"，自治程度完全不同：

```python
# 看起来在模块内部，实质是工程师越权——数字来自外部规定的阈值表，不是自己的历史
if available > 0.7:
    self.camera_size = 16

# 真正的模块自治——数字来自这一刻通报的事实，经过模块自己的换算逻辑
n_precise = int(self.n_cells * available)
```

前者本质上是把工程师的 if-else 决策树，从 `main.py` 搬进了模块的方法体里，**位置变了，决策权没变**——这是这几轮讨论里最容易被忽略、也是最该被抓出来的一种伪装成"模块自治"的越权。判断标准不是"这行代码物理上写在哪个文件"，是"这个值的产生过程里，有没有一步是工程师直接拍板、模块只是执行"。

### 5.2 这条主线在采样讨论里具体纠正过工程师本人（我）的地方

诚实记录，不是自我批评的姿态，是为了留一份"越权模式长什么样"的真实样本，供以后自查：

1. 最开始给出的所有 resize 方案，目标尺寸都是我直接给的数字（`64×64`、`16×10`、`32×24`），没有一次是从摄像头分辨率推导出来的——这个问题**至今没有被真正解决**，只是不断被搬到不同的常量名字上。
2. `camera_size` 三档硬跳变的密度调节，是我按"资源紧张就该采样粗一点"这个直觉直接写的 if-else 阈值树，属于典型的"决策权留在工程师手里、只是把执行代码放进了模块"。
3. 色阶权重、聚焦强度这些系数，从第一次给出实现开始就是拍的数字，从未真正交还给模块自己去校准——这不是笔误，是这几轮讨论里持续存在、但没被当作"越权"来对待的一处盲区，直到这一轮才被你指出来。

# CIMA0 Camera Sampling 最简原则 v1.0

## 1. Camera输入目的

摄像头不是提供图像。

摄像头提供：

> 外部扰动场。

输入目标不是还原画面，而是让内部动力系统受到有效扰动。

---

## 2. 模块职责

### camera_planet.py

负责：

> 摄像头硬件事实。

包括：

* 分辨率
* 帧率
* 原始帧

不负责：

* 采样
* 判断
* 理解

---

### camera_compute.py

负责：

> 计算系统自身资源状态。

根据自身算力决定可支持的计算量。

不负责：

* 理解图像
* 选择内容
* 修改规则

---

### camera_observer.py

负责：

> 摄像头采样。

将完整画面转换为内部状态。

负责：

* 空间覆盖
* 块平均
* 状态变化计算
* 采样竞争

不负责：

* 语义理解
* 控制内部动力

---

### camera_io.py

负责：

> 状态与字节流之间的同构转换。

只传输。

不解释。

---

# 3. 空间采样原则

禁止：

* 截断
* 固定取顶部/中心区域
* 丢弃大部分画面
* 改变输入拓扑

必须：

> 全画面覆盖。

---

# 4. 基础采样

采用：

> 确定性块平均。

流程：

```
Camera Frame

↓

均匀划分区域

↓

每个区域平均

↓

固定结构状态矩阵
```

不使用：

* 随机采样
* 不透明插值

---

# 5. 拓扑原则

输入结构必须稳定。

禁止：

```
资源变化
↓
网格数量变化
↓
系统重建
```

允许：

```
资源变化
↓
更新频率变化
↓
精细程度变化
```

---

# 6. 信息原则

内部需要的是：

> 状态变化，而不是静态图像。

因此：

主要信号：

```
δ = 当前状态 - 自身历史状态
```

静态：

```
δ ≈ 0
```

变化：

```
δ 增大
```

---

# 7. 精算原则

永远保持：

```
全画面粗采样
```

在此基础上：

根据计算能力：

```
部分区域精细计算
```

不是：

```
删除低价值区域
```

而是：

```
降低精度
```

---

# 8. 运动与颜色

主信号：

```
运动变化
```

辅助信号：

```
色阶变化
```

两者都使用：

```
自身时间差
```

不比较绝对值。

---

# 9. 人眼式聚焦

不改变网格。

不改变拓扑。

只改变：

> 哪些区域更容易获得精算机会。

---

# 10. 模块自治总原则

任何参数必须回答：

> 这个决定是谁产生的？

禁止：

工程师直接规定：

* 固定尺寸
* 固定阈值
* 固定优先级

允许：

模块根据：

* 当前状态
* 历史状态
* 输入事实

自行调整。

---

最终一句话：

> Camera负责提供完整外部扰动，Compute负责计算能力，Observer负责采样映射，IO负责传输；采样保持全覆盖、固定结构、时间自比较，只改变精度，不改变存在形式。
