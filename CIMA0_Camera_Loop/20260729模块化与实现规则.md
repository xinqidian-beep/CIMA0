CIMA0 模块演化与实现规则
模块归属优先原则

系统出现任何现象、问题或不足时，不直接增加规则、控制逻辑或新模块。

必须遵循：

发现现象

↓

分析现象属于哪一种能力

↓

定位负责模块

↓

修改该模块内部表达结构

↓

重新进行设计原则审计
内部表达结构原则

模块优化不是通过外部干预改变行为，而是通过调整模块自身的表达能力，使系统自然产生新的行为。

禁止：

通过外部控制修正结果；
增加针对特定现象的特殊规则；
使用中心模块协调局部模块；
为了达到预期结果添加人为目标。

允许：

修改状态表达；
修改局部变量结构；
修改内部关系表达；
修改局部交互形式；
修改时间尺度表达。

目标不是控制结果，而是让结构能够承载更多自然演化。

四模块问题归属规则
内部动力模块

负责：

状态表达；
局部相互作用；
动力演化；
时间推进。

当问题涉及：

演化轨迹；
稳定性；
局部耦合；
自发变化；

只修改动力模块内部表达。

IO模块

负责：

外界扰动进入；
原始信息边界传递；
输入输出边界保持。

当问题涉及：

输入格式；
字节流处理；
边界转换；

只修改IO内部表达。

禁止：

语义解释；
目标识别；
智能判断。
采样模块

负责：

有限观察；
局部投影；
稀疏扫描；
精度层级。

当问题涉及：

如何观察；
如何采样；
如何形成瞬时快照；

只修改采样结构。

禁止：

控制动力；
决定系统目标；
拥有全局视角。
计算模块

负责：

自身计算资源；
计算预算；
精度投入；
举手机制。

当问题涉及：

是否增加计算；
是否提高采样精度；
当前资源分配；

只修改计算模块内部表达。

禁止：

判断世界重要性；
修改动力状态；
成为中央控制器。
禁止跨模块修补原则

发现问题时：

禁止：

动力问题 → 修改Observer

采样问题 → 修改Planet

计算问题 → 修改IO

输入问题 → 增加Cloud控制层

正确：

问题属于谁

↓

谁内部演化

↓

谁负责表达
最终审计规则

任何代码修改完成后，必须检查：

是否引入全局状态？
是否产生隐藏控制者？
是否模块越权？
是否增加非必要结构？
是否通过改变表达结构解决问题，而不是通过外部修正？

只有全部通过，才进入下一阶段。

核心思想：

系统不是通过外部管理获得复杂性。

复杂性来自：

最小局部结构

↓

内部表达变化

↓

局部相互作用

↓

大尺度涌现

视角归属原则（Perspective Ownership）
任何问题产生之前，必须先确定：

提出问题的主体

↓

它属于哪个模块

↓

它拥有哪些可访问信息

↓

它是否有资格提出这个问题
例如：

问题：
外部输入如何影响内部？

先问：

谁提出？

如果是：

IO模块视角
它可以问：

我如何把边界数据传递出去？

因为 IO 的职责是边界交换。

如果是：

Observer视角
它可以问：

我观察到的局部变化与之前有什么不同？

因为 Observer 处理观测。

如果是：

Compute视角
它可以问：

当前资源是否足够支持更高精度观察？

因为 Compute 管理自身计算能力。

如果是：

Planet动力视角
这个问题就不成立。

因为 Planet 不拥有：

“外部”和“内部”的概念。

它只有：

当前状态

↓

局部关系

↓

下一状态
所以：

错误推理：

观察者的问题

↓

强行翻译成动力系统接口
例如：

“外部如何进入内部？”

↓

创建：

receive_disturbance()
这就是视角污染。

正确流程：

提出问题

↓

识别提问者

↓

检查该模块的能力边界

↓

判断问题是否属于它

↓

如果属于：
    修改该模块表达结构

如果不属于：
    重新定位问题
这个原则和前面的“模块归属原则”其实是一对：

模块归属
回答：

这个现象应该由谁负责？

视角归属
回答：

这个问题是谁有资格提出？

二者结合：

问题出现

↓

谁在问？

↓

谁拥有这个能力？

↓

哪个模块负责？

↓

修改内部表达结构

↓

原则审计
这也解释了为什么自然系统不会出现：

“细胞管理环境”。

细胞内部没有一个模块每天问：

外部世界为什么影响我？

它只是：

状态变化；

局部响应；

继续演化。

“外部环境”这个概念，是观察尺度为了压缩描述而产生的。

所以以后代码审计时，新增第一问：

这个需求是谁提出的？这个主体是否有资格拥有这个概念？

如果答案：

“不属于该模块”，就不要写代码。

先重新定位问题。

这个规则会进一步防止系统慢慢演化出一个隐藏的“上帝视角”。

# CIMA0 第三层规则：物理侧与语义侧隔离原则

## 一、基本原则

系统中存在两个不同层级：

```
物理侧（Physical Layer）

↓

语义侧（Semantic Layer）
```

二者不是同一个世界的两个对象，而是：

```
物理侧：
真实动力状态及其演化

语义侧：
观察过程对物理状态形成的有限描述
```

语义侧不能被当作新的物理实体。

---

# 二、物理侧定义

物理侧负责：

* 状态存在；
* 局部相互作用；
* 动力演化；
* 时间连续变化。

物理侧只处理：

```
state

↓

interaction

↓

next state
```

物理侧不知道：

* 自己被观察；
* 自己的重要性；
* 自己的意义；
* 自己属于哪个概念。

禁止物理侧出现：

```
cloud
feature
label
meaning
importance
attention
```

这些属于观察描述。

---

# 三、语义侧定义

语义侧来自：

```
物理状态

↓

有限采样

↓

压缩

↓

描述结构
```

产生：

* Cloud；
* Feature；
* Snapshot；
* Pattern；
* Label；
* Statistics。

这些不是物理对象。

它们是：

```
observer 对物理状态的局部投影
```

---

# 四、Cloud定义规则

Cloud不是：

* 第二动力系统；
* 环境实体；
* 内部物质；
* 独立状态空间。

Cloud是：

```
Observer 对局部物理状态的语义表达
```

例如：

物理侧：

```
局部状态矩阵变化
```

观察侧：

```
Cloud:

{
 region,
 variance,
 activity,
 pattern
}
```

其中：

矩阵是真实动力。

Cloud是描述。

---

# 五、禁止语义反物理化

禁止：

```
Cloud
    ↓
直接改变
    ↓
Planet动力规则
```

因为这相当于：

观察结果成为现实原因。

属于层级倒置。

---

允许：

```
Planet

↓

Observer

↓

Cloud

↓

Compute

↓

调整观察策略
```

即：

语义侧可以影响：

```
观察行为
计算资源
表达方式
```

不能直接修改：

```
物理动力状态
```

---

# 六、观察者限制原则

Observer永远只能获得：

```
物理系统的局部投影
```

不存在：

```
全局状态读取
```

不存在：

```
完整世界模型
```

任何观察结果都是：

```
局部采样
+
当前尺度
+
当前计算能力
```

产生的描述。

---

# 七、语义产生规则

任何概念必须检查来源：

如果来源是：

```
直接动力关系
```

属于物理侧。

如果来源是：

```
采样、压缩、比较、分类
```

属于语义侧。

例如：

| 概念         | 所属  |
| ---------- | --- |
| 状态变量       | 物理侧 |
| 邻域作用       | 物理侧 |
| 演化方程       | 物理侧 |
| Cloud      | 语义侧 |
| Feature    | 语义侧 |
| Snapshot   | 语义侧 |
| Importance | 语义侧 |
| Attention  | 语义侧 |

---

# 八、代码审计规则

修改代码前必须检查：

## 问题：

这个变量来自哪里？

如果来自：

```
动力演化
```

可以进入物理模块。

如果来自：

```
观察计算
```

必须停留在语义模块。

---

## 禁止：

```
Observer变量
        ↓
Planet状态
```

```
Cloud变量
        ↓
动力方程
```

```
Feature变量
        ↓
物理规则
```

---

# 九、最高检查问题

任何新增模块、变量、接口前，必须回答：

1. 它描述的是现实状态，还是观察结果？

2. 它来自动力演化，还是采样压缩？

3. 它属于物理侧，还是语义侧？

4. 如果删除观察者，这个东西是否仍然存在？

如果删除观察者后不存在：

它就是语义结构。

---

核心原则：

```
物理产生变化。

观察产生描述。

计算调整观察。

语义描述不能替代物理存在。
```
