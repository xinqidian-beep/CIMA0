# CIMA0 模块自治操作手册 v1.0

> 配套文档：《CIMA0_设计约束与框架_v1.0.md》（原则与审计记录）。
> 本手册是原则的**操作化**：告诉写代码的人，遇到"这个数字该怎么定/这个行为该谁决定"
> 这类问题时，标准答案该往哪个方向找，而不是直接给出一份可以抄的固定实现。
>
> **核心执行姿态：外部工程师的工作是搭好模块之间的管道（接口契约），
> 不是替任何一个模块做决定。凡是"这个值该是多少/这次该怎么做"这类问题，
> 答案必须能在模块内部、依据它自己的状态和历史推出来——推不出来，
> 说明设计还没想清楚，不能用外部传参数这种方式绕过去。**

---

## 1. 放权的操作定义

"放权"不是一句态度声明，是三条可以直接拿来检查代码的硬性判据：

### 判据 A：接口只传"事实"，不传"指令"

一个模块的公开方法，参数里**允许**出现的东西：
- 原始数据（帧、字节流、数组）
- 只读状态快照（"当前可用资源是多少"、"当前这块区域的历史值是多少"）

**不允许**出现的东西：
- 任何形式的"你应该怎么做"（模式开关、阈值参数、目标值、"精度等级"这类由外部指定的行为参数）

判断方法：把参数名读一遍，如果读起来像"命令"（`set_mode`, `force_precision`, `target_size`），就是违规；如果读起来像"事实通报"（`update_resource(compute_state)`, `receive(frame)`），就是合规。

### 判据 B：模块的内部参数，必须能写出"为什么是这个值"的推导链，而不是一个裸常数

不要求这条链条多么严谨，但必须存在。比如：
- ❌ `fovea_strength = 1.6`（拍出来的数字，问"为什么是 1.6"答不上来）
- ✅ `n_precise = int(n_cells * available)`（能说清楚："预算比例直接线性映射到能精算的格子数，这是当前能想到的最简单假设，等真实开销数据出来后再调"）

**允许"暂时没有推导，先用一个数字占位"，但必须在代码注释或手册的"待校准参数表"（见 §5）里显式标注为待定，不能悄悄当成定案。**

### 判据 C：跨模块的信息传递方向，必须能在 §2 的表格里找到对应行；找不到对应行的新连接，先补表再写代码

这条是防止"顺手加一条新的调用关系"在实现层面悄悄发生、但没人意识到这是一次新的架构决定（参考：约束文件 §2.4 反馈回路的教训——事后发现的架构决定，比事前记录的架构决定，处理成本高得多）。

## 2. 模块自治权限表

这张表是全手册的核心，每一行回答两个问题：**这个模块自己决定什么**，**它从外部只被动接收什么事实（不接收指令）**。

| 模块 | 自己决定（内部权限） | 只读接收（不可指令化） | 绝不接收 |
|------|---------------------|----------------------|---------|
| `ComputeSystem` | 当前可用资源有多少、这次分配多少出去、恢复速率 | 无（它是资源的唯一权威源，不看任何外部状态） | 谁在申请、申请来干什么、这次请求"重不重要" |
| `CameraObserver` | 用多少预算做精算、精算哪些格子（举手竞争）、注视点在哪、色阶级数怎么量化 | 当前帧（事实）、`compute_state`（事实：还有多少资源） | 外部指定"这次采样密度设为 X"、外部指定"这块区域优先" |
| `CameraPlanet` | 自己的局部动力学怎么演化、要不要接受外部力的调制 | 外部映射后的数值状态 | 外部指定"你现在该表现出什么状态" |
| CIMA Core（各振荡节点/耦合边） | 自己和邻居的相位关系、耦合强度怎么随经验漂移 | 邻居的局部状态（仅限拓扑相邻者） | 任何全局状态、任何"这次该同步/该分裂"的指令 |
| `projection` | 无自主决策空间——这是纯格式转换层 | 内部状态快照 | （此模块本身不持有决策权，是唯一允许"没有自治权"的层，因为它的职责定义就是零判断） |
| `camera_io` / `display_io` | 无自主决策空间——纯透传边界 | 上下游的原始数据 | 同上 |

**读这张表的方式**：中间那一列（"只读接收"）里出现的每一样东西，进入模块后，**这个模块拿它做什么、做多少，完全是模块自己的事**，外部调用者写完 `observer.update_resource(compute_state)` 这一行之后，不需要、也不应该关心 `CameraObserver` 内部具体怎么用这个数字——那是它自己的决策空间。

## 3. 决策逻辑手册（逐模块）

### 3.1 ComputeSystem：如何决定"这次分配多少"

**它知道的全部东西**：自己的历史分配记录（`available`, `capacity`, `decay`）。它不知道谁在要、要来干嘛。

**决策逻辑**：
```
每一步：
    available 向 capacity 自然恢复（速率由 decay 决定，这本身也该是可随经验调整的内生量，
                                    而不是外部一次性给定的常数——如果暂时做不到，
                                    先记入 §5 待校准表）
接到一次 allocate(signal) 请求：
    signal 被裁剪到 [0,1]（防止请求方传入越界值污染内部状态——
                            这不是"理解请求"，是自我保护，允许）
    budget = available * signal
    available -= budget，下限钳制在 0
    返回 budget，仅此而已，不问这笔预算被谁拿走后做了什么
```

**外部工程师唯一该做的事**：调用 `compute.allocate(signal)`，把返回的 `budget` 转发给需要它的模块。**不该做的事**：根据"我觉得这次很重要"去手动调高 `signal`——`signal` 该是某个模块基于自己状态算出来的数字（比如 observer 算出的举手强度总和），不是工程师现场评估出来的。

### 3.2 CameraObserver：如何决定"这次精算哪里、精算多细"

这是当前系统里自治逻辑最复杂的一层，分四个子决策，每个子决策都该是模块内部自己算出来的：

**子决策 1：基线怎么采（永远发生，不受预算影响）**
- 固定网格、块平均、确定性遍历——这部分**不是决策**，是原则 1（不截断/均匀覆盖）直接推出来的唯一合规做法，不存在"要不要这样做"的选择空间，写死即可，不算违反"放权"。

**子决策 2：谁该被精算（举手竞争）**
- 依据：自身状态的时间差 δ（运动为主、色阶为副，色阶受运动门控）
- 排名依据 δ 大小，不依据"外部觉得这块重要"
- **这个决策的输入只能是模块自己观察到的历史，不能是外部传入的"关注区域"参数**

**子决策 3：精算的名额有多少**
- 依据：`compute_state["available"]` 换算出来的预算，换算公式本身允许简化假设（线性映射），但换算逻辑必须写在模块内部，不能是外部传入"这次精算 N 个"这样的指令

**子决策 4：注视点在哪（人眼式聚焦）**
- 依据：运动质心的指数平滑跟随 + 无运动时向中心回归——**这两个系数（跟随速度 0.3、回归速度 0.95）目前是拍的**，按判据 B 需要标注进待校准表

**外部工程师唯一该做的事**：
```python
observer.update_resource(compute.snapshot())   # 通报事实
state = observer.sample(frame)                  # 接收结果，不干预过程
```

### 3.3 CameraPlanet / CIMA Core：如何决定"要不要理会外部输入、理会多少"

**当前已确认的架构决定（见约束文件 §2.4）**：Planet 的演化规则本身**不接受**外部输入直接改写状态，只允许外部输入作为一种"力"参与到已有的局部动力学方程里（如果这条要保留，需要先把这次讨论的采样结果，通过一个明确的"力注入"接口喂给 Planet，而不是像当前代码那样让 Planet 完全孤立于 `external_state` 之外——这是待修复项，见约束文件 §8 已知偏离记录）。

**决策权**：Planet 自己的相位、振幅怎么响应这个力，是它自己方程里的系数决定的，不是外部说了算。外部只负责把"这个格子这次有多大的力"这一份事实喂进去。

### 3.4 举手竞争的通用范式（跨模块复用的一条元规则）

任何"多个候选者、一份有限资源、谁该拿到"这类问题，标准解法都是同一个范式，不要为每个新场景发明新的分配逻辑：

```
1. 每个候选者产出一个"自比较差值"（当前状态 - 自身历史状态）
2. 差值转换成统一量纲的评分（必要时可乘以一个空间/时序先验权重，如注视点距离）
3. 按评分排序，取前 N 名，N 由外部通报的资源事实换算得出
4. 胜者获得资源；败者的默认输出保持"退化但形状恒定"的基线值，不是空值/缺失
```

`CloudInjector` 的竞争认领、`CameraObserver` 的举手精算，都是这个范式的实例——以后新增任何"分配式"逻辑，先看是不是能套这个范式，不要重新发明。

## 4. 反模式清单（提交前逐条自查）

| 反模式 | 为什么是违规 | 正确做法 |
|--------|-------------|---------|
| `observer.set_camera_size(64)` | 外部直接下指令，剥夺了模块自己依据 `compute_state` 决定密度的权限 | `observer.update_resource(compute_state)`，密度由模块内部算 |
| `compute.allocate(signal=1.0)  # 因为这次很重要` | `signal` 是工程师现场评估出来的主观判断，不是某个模块自身状态的产物 | `signal` 必须来自另一个模块的客观计算结果（如举手强度总和），工程师只做转发 |
| 在 `main.py` 里写 `if energy > 0.5: mode = "excited"` | 语义判断被塞进了不该有语义的胶水层，且这类判断在任何模块内部出现也同样违规（原则 5、CIMA Core 命名铁律） | 这类"意义"只允许存在于系统之外的观察者脑子里，代码里任何一层都不该写 |
| 新增一个跨模块调用，但 §2 权限表里没有对应行 | 说明这是一次没被记录的架构决定，风险和"悄悄加反馈回路"是同一类问题 | 先补 §2 表格 + 约束文件 §2.4/§6，再写调用代码 |
| 精算 gLoss/密度参数写死在 `__init__` 的默认参数里，且从未被使用它的模块自己更新过 | 常量位置对了（在模块内部），但如果它从来不随经验/输入变化，本质上还是外部一次性写死，只是搬了个位置 | 至少要有一条路径，让这个参数能被模块自己的运行历史修改（即使更新规则很简单） |

## 5. 待校准参数表（当前已知，尚无推导依据，允许暂用但必须标注）

| 参数 | 当前值 | 所在模块 | 校准方式（建议） |
|------|--------|---------|-----------------|
| 色阶副信号权重 | `0.3` | `CameraObserver.sample` | 跑起来看运动/色阶评分的数值分布，按经验分位数对齐后再定 |
| 注视点跟随速度 | `0.3` | `CameraObserver._update_fovea` | 同上，或参照人眼扫视的真实时间常数（约 20-200ms）反推 |
| 注视点回归速度 | `0.95`（每步衰减系数） | `CameraObserver._update_fovea` | 同上 |
| 聚焦强度 | `1.6` | `CameraObserver._fovea_weight` | 视觉实验：调整后观察精算区域集中程度是否符合预期 |
| 色阶级数 | `5` | `CameraObserver._posterize` | 视觉实验：级数太低会丢失色彩层次，太高失去"动画感" |
| `ComputeSystem.decay` | `0.01` | `ComputeSystem` | 目前是外部一次性给定常数，按判据 B 属于待改造项——理想情况下这个值也该是内生慢变量 |

> 这张表存在的意义：允许开发过程中"先用一个数字跑起来"，但强制要求这个数字被显式记录为**暂定**，
> 防止它在后续迭代里被误当作"已经想清楚的设计决定"。每次校准后更新此表，不要删除旧记录，
> 加一行版本注记即可。

## 6. 外部工程师的标准工作流（写新模块/新功能时，按这个顺序检查）

```
1. 这个新东西需要做什么决策？
   → 列出所有"这次该怎么办"类型的问题

2. 每一个决策，能不能只依据"这个模块自己的历史状态 + 只读事实通报"推出来？
   → 能：决策逻辑写在模块内部，继续 3
   → 不能：说明这个决策本质上依赖某种"重要性判断"或"全局视角"，
           先停下来讨论这是否违反原则 4/5，不要为了推进而妥协

3. 这个决策需要的"只读事实"，来自哪个模块？
   → 检查 §2 权限表有没有对应的信息流向
   → 没有：先补表，明确这是一次新的架构决定，记录理由
   → 有：直接复用已有的 snapshot/update_resource 类接口，不新增指令型方法

4. 决策里用到的具体数字，能不能推导，还是先拍一个？
   → 能推导：写出推导依据（哪怕很粗糙）
   → 拍的：登记进 §5 待校准表，不要不登记就当作定案

5. 写完后，用 §4 反模式清单逐条过一遍
```
