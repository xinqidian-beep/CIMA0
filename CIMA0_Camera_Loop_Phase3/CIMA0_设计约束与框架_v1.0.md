# CIMA0 设计约束与框架 v1.0

> 本文档是对既往所有讨论的收敛，不是新设计。后续每一次迭代，先对照本文档，
> 有冲突时，本文档优先于任何单次讨论中临时产生的想法——除非明确修订本文档本身。

---

## 0. 核心哲学定位（一句话）

**不要有任何外部强加、中心化、单方面规定的东西，一切该由系统内部的局部规则自己长出来。**

这句话是六条原则的共同来源，任何一条原则的合理性最终都可以追溯到这里。
判断一处设计是否合规，最快的方法就是问：**这个数字/这个连接/这个决定，是外部一次性给定的，还是从系统内部或输入结构里推导出来的？**

## 1. 六条核心原则

| # | 原则 | 一句话判据 |
|---|------|-----------|
| 1 | 摄像头输入不能被截断/降采样丢弃 | 要么全采，要么均匀覆盖；不能挑、不能裁、不能只取一部分 |
| 2 | Cell 的规模、拓扑不能是外部一次性写死的常数 | 尺寸/连接关系必须能从输入结构（如摄像头分辨率）推导出来 |
| 3 | 注入不能是外部指定谁对应谁 | 要么竞争认领，要么整体云注入产生互动，不能硬编码映射关系 |
| 4 | open_clip 不是外挂翻译器，是世界里的一个结构 | 不该有特权广播通道；它的输出该和其它信号一样参与局部竞争/演化 |
| 5 | 内部自洽，外部不需要理解内部发生了什么 | 外部只读一个简单输出（举手/变化），不读内部状态细节 |
| 6 | 能靠逻辑推导的，就不需要用运行去验证 | 写代码前先能在纸面上说清楚会发生什么，测试用来确认，不用来探索 |

### 1.1 原则详解与常见违反模式

**原则 1（全采/均匀覆盖）**
- ✅ 合规：确定性遍历全画面切块（如 `bgr_to_spatial_blocks` 逐块扫描）；块平均（block reduce）
- ✅ 合规：均匀网格 resize（`cv2.resize` 到目标尺寸），只要目标尺寸本身满足原则 2
- ❌ 违反：只取画面某一部分（如"前 128 字节"、"左上角 16×16"）
- ❌ 违反：`CenterCrop` 之类会整块丢弃画面区域的操作
- ❌ 违反：基于运动强度的 Top-K 选择性丢弃（除非明确认可"注意力式非均匀采样"这一分支，见 §4.3）

**原则 2（拓扑非外部写死）**
- ✅ 合规：`N = DOWN_W * DOWN_H`，其中 `DOWN_W, DOWN_H` 由摄像头原生分辨率和一个"采样密度"参数计算得出
- ❌ 违反：`H, W = 64, 64` 这类直接写死的常量，与输入分辨率无关联
- ⚠️ 灰色地带：`DOWN_W, DOWN_H` 本身仍需要人指定一个"密度"旋钮（如 `cell_px`），这是允许的——原则约束的是"格子数量"不能直接写死，不是"密度参数"不能存在。密度参数是唯一允许保留的旋钮。

**原则 3（竞争认领/整体互动）**
- ✅ 合规：`claim_score` 竞争认领机制（结构相似度 + 可用性 + 新鲜度加权，胜者获得输入）
- ✅ 合规：认领权重本身作为 Cell 内生慢变量，随经验漂移（需满足 §5.2 的两个限制）
- ❌ 违反：固定权重线性叠加、外部指定"这个区域的输入永远给这个 Cell"

**原则 4（open_clip 非特权通道）**
- ✅ 合规：CLIP 输出的结构（如 patch 级特征图）以和其它信号同形的方式参与局部竞争/叠加，不整体压成标量后广播
- ❌ 违反：CLIP embedding 绕过所有局部机制，直接写入全局状态或触发全局响应
- ❌ 违反：CLIP 的标准预处理（`Resize`+`CenterCrop`+`Normalize`）被直接拿来当作系统的采样层——这本身就同时违反原则 1（CenterCrop 截断）、原则 2（224 是库内部写死的常量）、原则 4（CLIP 库本身的假设被当成系统架构的一部分）

**原则 5（外部只读简单信号）**
- ✅ 合规："举手"机制：`raised = activity > baseline * 1.3 and activity > threshold`，Observer 只返回 `raised=True` 的 Cell
- ❌ 违反：外部直接读取 `mean`、`std`、embedding norm 等连续统计量作为主要输出接口（这些可以内部使用，但不该是"外部观察者"默认拿到的东西）
- ❌ 违反：举手机制被整体移除，改为直接显示原始数值的线性映射

**原则 6（能推导不用跑）**
- 方法论原则，不对应具体代码模式。适用场景：加一个新机制前，先手推它在几个边界情况下（无输入、单点输入、饱和输入）会收敛到什么状态，再写代码。

## 2. 系统分层架构

### 2.1 管线（当前确认版本）

```
hardware/usb_camera.py          [硬件适配层，仅访问硬件]
        |
        v
core/camera_io.py               [输入边界：纯透传，不采样不计算]
        |
        v
core/camera_planet.py           [外部映射层：帧 -> 数值状态，允许归一化，不允许解读]
        |
        v
core/camera_observer.py         [自比较层：与自身历史状态求差 δ，产生 ephemeral 信号]
        |
        v
core/camera_compute.py          [资源竞争层：δ 信号竞争计算预算，产生 grant]
        |
        v
[CIMA Core / 动力核心]           [见 §2.3，纯局部规则集合，无全局视角]
        |
        v
core/projection.py              [稀疏投影：把内部状态重建为可显示帧]
        |
        v
core/display_io.py              [输出边界：纯透传]
        |
        v
hardware/display_device.py      [硬件适配层]
```

### 2.2 各层职责边界（硬约束）

| 模块 | 允许做 | 禁止做 |
|------|--------|--------|
| `camera_io` | 原样传递帧 | 采样、压缩、特征提取、状态判断 |
| `camera_planet` | 接收、数值归一化、局部演化（自己的动力学规则） | 采样、计算资源分配、语义理解、跨帧长期记忆判断（除非该记忆本身是"演化状态"的一部分） |
| `camera_observer` | 与自身历史状态做自比较，产生 δ；生成"计算需求"信号（仅是 raise 信号，不代表分配结果） | 图像理解、采样分配、计算分配、优先级判断、控制、预测 |
| `camera_compute` | 估计自身可用计算资源、自然恢复、响应临时请求并批出 grant | 图像理解、采样决策、优先级判断、控制、长期记忆 |
| `projection` | 数据格式转换（内部状态 -> 显示帧） | 判断、过滤、解读 |
| `display_io` | 原样传递帧到硬件 | 计算、观察、解读 |

### 2.3 CIMA Core：动力核心，不是语义核心

- **命名铁律**：任何写作 "Core" 的模块/文件夹，字面意思必须严格限定为"拓扑意义上连接最密集的一层"，绝不能默认代入"中央认知/语义理解"的联想。如果一个文件夹命名为 `core/` 但装的是外周组件（observer、compute、projection、display_io），需要改名（如 `pipeline/`），把 `core` 这个词留给真正的动力核心专用。
- **核心不知道全局**：每个动力单元（振荡节点、耦合边）只感知直接相连的局部邻域，没有任何组件能访问"系统当前处于什么状态"这种全局信息。
- **全局是涌现表达，不是内禀属性**：`energy`、`coherence` 一类的全局统计量，是外部观察者对状态做的聚合，系统自己不"知道"这些数字。
- **意义完全不存在于系统内部**：任何"这个信号代表什么"的问题，都不该在系统内部预设答案，只能留给系统之外的观察者。写代码时如果发现自己在给某个内部变量赋予语义解释（"这代表愤怒""这代表专注"），这是违反本条的信号。

### 2.4 数据流方向：严格前馈，无反馈回路

- CIMA Core 的演化结果只流向 `projection` → `display_io`，**不会**反向影响 `camera_planet`/`camera_observer`/`camera_compute` 下一步的行为。
- 这个约束是**刻意的、已确认的**，不是遗漏。理由：系统的"内在状态"不应该有能力索取更多感知资源或改变自己"看"世界的方式——外周对内部状态保持中立，核心的选择性/适应性完全通过自身内部结构的可塑性（如 Hebbian 式耦合强度调整）实现，而不是通过重新分配感知资源实现。
- 如果未来要引入反馈回路，必须先在本文档里作为一次**独立的、明确记录的架构决定**写下来，不能在实现中悄悄加一条箭头。

### 2.5 camera_io / display_io：同构而非同一

- 输入边界和输出边界是**同一套接口契约（角色）的两个独立实例**，不是同一个对象、也不要求同名文件/同一个类。
- 允许两者在具体实现上完全不同（不同的缓冲策略、不同的硬件后端），只要它们各自都满足"纯透传、不解读"这一条职责边界。

## 3. 采样层规范（当前最容易违反的一层，重点检查）

### 3.1 判断标准

一个采样实现是否合规，按顺序检查：

1. **是否用了外部库的默认预处理（如 `open_clip` 自带的 `preprocess`）来做系统的主采样层？**
   → 如果是，几乎必然违反原则 1（内含 CenterCrop 截断）+ 原则 2（内含库自己写死的输入尺寸）+ 原则 4（把第三方库的假设当成了系统架构）。**这是当前已确认存在于代码里的违反，见 §8。**

2. **目标网格尺寸 `(H, W)` 是不是从摄像头原生分辨率 + 一个密度参数计算出来的？**
   → 如果是写死的常量（`64, 64` / `16, 10` / `32, 24` 等直接出现在代码里的数字），违反原则 2。

3. **降采样用的是插值（`cv2.resize` 默认双线性/双三次）还是块平均（reshape + mean）？**
   → 插值不是严格意义上的"均匀覆盖"（权重不透明、可能产生混叠），块平均是。两者都比"截断/选择性丢弃"合规，但块平均更贴近原则 1 的字面要求。如果追求最严格合规，优先块平均。

4. **切块/取点过程里有没有 `np.random`？**
   → 除非是"人眼式非均匀密度采样"这一分支下经过明确设计的动态过程（见 §4.3），否则采样阶段不应该有任何随机性。确定性遍历全画面是默认要求。

### 3.2 标准合规实现模板

```python
def sample_frame(frame, cell_px):
    """
    frame: 摄像头原生分辨率的 BGR 帧，不做任何缩放
    cell_px: 密度旋钮，每个 cell 覆盖多少原始像素（这是唯一允许的外部常量）
    """
    native_h, native_w = frame.shape[:2]
    H = native_h // cell_px
    W = native_w // cell_px

    trimmed = frame[:H*cell_px, :W*cell_px]          # 裁掉除不尽的余数，不插值
    patches = trimmed.reshape(H, cell_px, W, cell_px, 3)
    grid = patches.mean(axis=(1, 3))                  # 块平均，每个像素恰好属于一个 cell

    return grid, H, W   # H, W 用于同步派生 Cell 拓扑（原则 2）
```

### 3.3 颜色通道规范（已确认合规，保持）

- 全程 BGR，不做 `cvtColor` 转 RGB。采集是 BGR，内部状态是 BGR，显示也按 BGR 规格写出。
- 若显示后端（如 PIL/Tk）默认按 RGB 解释，**不加"纠正性"转换**——保持同构比保持视觉正确更优先。如需正确颜色显示，换用原生支持 BGR 的后端（如 OpenCV 窗口），而不是在数据里加转换。

### 3.4 关于"人眼式/动画式"采样的引用（尚未定案，需先决策才能实现）

- **动画式（色阶量化/posterize）**：只影响"每个 cell 存什么值"，不影响拓扑。可以直接叠加在 §3.2 的标准实现之后，不与任何已确认原则冲突，可随时实现。
- **人眼式（中央凹/非均匀密度）**：只影响"cell 该分布在哪"。与均匀网格架构（`build_grid_neighbors` 假设规整矩形邻接）存在结构性冲突，需要先决定：
  - (a) 保持均匀网格，放弃非均匀密度这个分支；或
  - (b) 重新设计非规整拓扑下的邻接关系构造方式，并明确"中央凹中心点"由什么决定（固定 vs 跟随运动质心 vs 其它）——中心点若跟随运动，需要额外的运动检测逻辑，这本身是否违反"采样层不做计算"这一边界，需要一并决策。
  - **在明确选择 (a) 或 (b) 之前，不要实现任何非均匀密度采样代码。**

### 3.5 运动优先、色阶次要（已确认原则，尚未落地）

- 前提共识：现实中物体自发变色的情况远少于物体运动，因此运动应作为主信号，色阶为附加/门控信号，不是并列的独立通道。
- **"举手"的可比性原则**：运动信号和色阶信号要能在同一把尺子上比较，必须都取**自身状态的时间差值（δ = 当前 − 历史）**，而不是比较"运动的变化量"vs"色阶的绝对值"。两者结构必须同构（都是自比较产生的差值）才具备公平竞争的资格。
- 色阶只在运动 δ 非零的区域保留（门控），不该在静止区域独立产生举手信号。
- 待决策项：
  - 是否引入多时间尺度的自比较（短时 vs 长时记忆），用于区分"真实持续变化"和"传感器噪声"；
  - δ 的数值分布在两个通道间是否需要归一化，还是保留色阶量化台阶带来的"断层式举手"作为一种刻意保留的美学特征；
  - 竞争仲裁的粒度是全局（整帧一个赢家）还是局部（分区各自竞争）。

## 4. 命名规范（已确认铁律，需在每次新增模块时检查）

- `*Planet`：外部世界的局部动力学镜像，不做采样/计算/解读（见 §2.2 表格）。
- `*Observer`：只读、只做自比较，不做分配决策。
- `*Compute`：只管理自身资源额度，不知道请求来自哪里、代表什么。
- 任何命名为 `Core` 的模块，字面含义必须是"拓扑核心"，不能默认暗示"语义/认知核心"（见 §2.3）。
- 命名一旦可能让协作者（包括未来的你）产生"这里在理解/判断/决定重要性"的联想，就需要改名或加注释明确排除该联想。

## 5. 权重/参数可塑性规范

若某个机制的参数（如认领权重 `w_affinity`, `w_avail`, `w_fresh`）要设计成随经验漂移的内生变量，必须同时满足：

1. **慢更新**：学习率要小（如 `lr = 0.02` 量级），防止参数在单次交互后剧烈震荡。
2. **归一化或投影回有限区间**：防止无限发散，防止 `claim_score` 被某个权重的无界增长变成任意放大器。
3. **只受局部反馈驱动**：更新依据必须是"这次用了这组权重之后，自己的状态有没有变得更健康（如 activity 没有立刻衰减）"，不能是外部给定的目标函数或奖励信号。**这是判断"权重可塑性是否破坏自洽"的唯一标准**——外部目标函数驱动 = 破坏自洽；局部经验驱动 = 不破坏。

## 7. 每次迭代前的自查清单

在提交任何新代码之前，逐条过一遍：

- [ ] 有没有新出现的写死常量？如果有，它能不能从输入结构/已有参数推导出来？
- [ ] 有没有新的一一映射关系（"这个输入固定对应这个内部单元"）？如果有，是不是该换成竞争/整体互动？
- [ ] 有没有任何模块的输出，被外部当作"内部状态的详细读数"来使用，而不是"一个简单信号"？
- [ ] 有没有在核心动力层和外周之间新增反馈路径？如果有，是否已作为独立决定写入本文档 §2.4？
- [ ] 新模块的命名，会不会让人误以为它在"理解"或"判断重要性"？
